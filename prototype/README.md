# 刚好·净省凑单 v1.4

外卖结算前的凑单决策原型。当前购物车达到起送条件时，比较加购前后实付，只推荐实付下降的净省方案；未达到起送条件时，另行寻找满足起送要求的补单方案，并明确展示补单后实付和相对旧估算的增支或减少。**原车不可下单时的估算差额不计为净省。**

1.3 新增起送门槛、用户偏好、最多四件的精确组合搜索和商品包装费；1.4 新增「符合我的偏好」排序——按本机演示事件中的品类权重对方案次序做演示级重排（标注为演示级，不改变方案内容与金额），看板将起送补单采纳呈现为「起送转化（不可下单→可下单）」口径，方案区显示服务端实时计算耗时。默认示例商品小计仍为 ¥48，常规时段实付 ¥35；采纳 ¥2 米饭净省方案后实付 ¥32，预计净省 ¥3。商品与优惠均为示例，尚未对接平台或创建真实订单。

## 启动

需要 **Node.js 20 或更新版本**，第三方依赖只有 Express 和 CORS。

- Windows：双击 `start-demo.bat`。首次自动安装依赖，启动本机服务并打开联动版；关闭「NetSave Backend」窗口停止服务。
- 手动启动：

```powershell
cd C:\Users\lenovo\Desktop\chuangxin\prototype\backend
npm install
npm start
```

服务默认监听 `127.0.0.1:3000`，同时提供页面与 API。打开 [http://127.0.0.1:3000/](http://127.0.0.1:3000/) 即可进入演示中心，无需另启静态服务器。

## 演示流程

1. 在联动版点击「满减净省示例」，核对商品小计 ¥48；比较最多三种方案，展开明细查看满减、优惠券、商品包装费和配送费。
2. 采纳默认米饭净省方案，常规时段实付 ¥35 → ¥32；高峰配送附加费同时影响前后金额。
3. 设置最多加购件数（0–4）、加购商品预算、排除商品或「支出更低／购买件数更少」。设置为 0 件表示不加购；约束内没有可行方案时明确显示无方案。
4. 点击「起送补单示例」，商品小计 ¥20，低于默认起送价 ¥25；查看起送补单。核对「补单后实付」和「额外增支／估算减少」，以及「原车不可下单」提示，勿将此差额解释为节省。
5. 打开看板，约 2 秒内看到有效采纳分类、预计净省及性能变化。起送补单采纳增加采纳数，但不增加累计预计净省。
6. 撤销最近一次采纳，核对购物车恢复和统计变化。进入操作记录页筛选撤销，原采纳仍保留并标注；起送补单撤销不显示净省扣回。
7. 点击「满减净省示例」后打开方案并选择「不加购」，检查忽略数与采纳率，再导出 JSON 或 CSV。

恢复示例不清空历史。刷新联动版会恢复本浏览器购物车及待确认操作，并向服务端核对状态；报价过期或发生变化时需重新计算。仅手动添加商品不等同于采纳建议。

## 本地任务评估

[任务评估页](http://127.0.0.1:3000/research.html)使用冻结的商品、优惠和计价时点，提供“差一点到起送价”和“差一点享受满减”两个任务，加购商品预算固定为 ¥10、最多 3 件。研究员填写匿名编号并选择手动判断或显示智能方案，再记录任务用时、选择、金额预估与简短反馈；手动方式不显示推荐排序。

任务记录只保存在当前浏览器，可导出 JSON/CSV 或清除；参与者编号、计时和问卷结果不会作为业务事件写入服务端。求解和金额复算由本机研究接口完成，使用独立示例和计算实例，不进入产品采纳率、累计净省、操作历史或业务计算性能窗口。浏览器数据不等同于跨设备存档，请在需要时导出保存。同一浏览器请一次只运行一个任务；多页面保存的不同已完成记录可合并读回，但不支持并行开展未完成任务。

此入口是本地评估工具，**没有随机分组，也不代表已经完成真实用户实验或证明业务效果**。任务方式和顺序需由研究员按方案安排；未实际招募参与者的记录只能作为演示数据。请使用随机匿名编码，不输入姓名、电话或账号。真实用户测试和平台 A/B 仍需按[技术方案](docs/TECHNICAL_SOLUTION.md)第 8 节另行实施。

## 计价与算法边界

```text
可下单基线：净省 = 当前实付 − 加购后实付，仅保留净省 > 0 的可行方案
不可下单基线：寻找达到起送门槛的补单；净省固定为 0
实付变化 paymentChange = 补单后实付 − 原购物车估算实付
```

默认起送门槛为 ¥25，以限时价生效后的**商品小计**判断，不包含包装、配送，也不扣满减或优惠券。引擎以服务端目录、库存和优惠为准，金额按分计算，商品 `packagingFee` 可选、缺省为 0。完整计价顺序见 [算法模型](docs/ALGORITHM_MODEL.md)。客户端价格不能改变结果。

搜索覆盖最多四件加购的数量组合，包括库存允许的同品多件。`maxItems` 限定 0–4，API 缺省为 2；API 缺省商品预算不限。联动页首次默认最多 3 件、商品预算 ¥10，保存过的偏好会恢复。`maxAdditionCost` 为 0–1000 元或不设上限，约束加购商品金额，不含包装及配送变化；`excludeIds` 排除商品；`strategy` 为 `saving`、`fewer` 或 `preference`，对应「支出更低／购买件数更少／符合我的偏好」。空购物车不推荐，已在车内的商品不再次作为候选。引擎在所给目录、库存、计价规则和这些约束内枚举可行解，返回最多三种可比较方案；「精确」只针对这一有限问题，不代表全平台最优。三种策略的排序、起送分支和相同分数的稳定规则见算法文档。

`preference` 策略是**演示级**功能：服务端从本机演示事件统计品类权重（采纳净省 +1、采纳补单 +0.5、忽略 −0.75、撤销 −1.5，截断到 ±3），据此微调方案展示次序，方案内容、金额与采纳复核口径不变。它基于本机演示行为，不是经真实用户数据训练的推荐模型，不预测用户意愿；看板「清空演示数据」会一并清空这些权重。

搜索规模随候选商品数和四件数量组合增长；当前无大规模商品目录的生产性能承诺。未对接跨店优惠、真实账户券、平台动态价格、用户口味或支付对账。它是显式规则与组合优化，不是经用户数据训练的机器学习推荐。

建议有效期 5 分钟，采纳前重新核对价格、库存、优惠与方案可行性；变化时要求重新计算。起送补单会增加消费也可能降低不可成交旧估算，均不据此宣传净省。

## 看板与记录口径

- 展示次数：实际打开并成功记录的建议数，单纯计算不算展示。
- 采纳／忽略：同一建议只能有一个最终选择；重试幂等。每次采纳可撤销一次，保留原事件且不重新变为待决定。
- 有效采纳：全部未撤销采纳，含净省方案与起送补单；分类计数分别为 `savingAcceptedCount` 和 `minimumOrderAcceptedCount`。
- 采纳率：有效采纳 ÷（有效采纳 + 忽略）；未决定及已撤销建议不进入分母，分母为零显示空状态。
- 累计预计净省：未撤销净省方案的正净省总和。起送补单贡献 0，**不是已支付订单的实际节省**。
- 平均采纳净省：累计预计净省 ÷ 全部有效采纳数，**包含起送补单的 0 贡献**；无采纳时为空状态。
- 近 7 天净省按 `Asia/Shanghai` 的采纳日期汇总，剔除已撤销采纳；起送补单不贡献金额。
- 算法性能：当前进程最近最多 1000 次实际计算的平均耗时和 P99，无样本为空；重启重新采样。

看板每 2 秒读取本机服务，失败时保留最后成功快照并标明状态。历史页在进入、返回前台或手动刷新时更新，支持采纳／忽略／撤销筛选及 `before` 游标分页；`total` 为当前类型全部匹配条数。所有统计只来自联动版的本地演示，不填入预设准确率或业务订单。

记录中 `kind` 为 `saving` 或 `minimum-order`；旧记录缺少 `kind` 按净省方案兼容。`newTotal`、`additionCost`、`paymentChange` 为元数值，最后一项可为负。净省采纳的 `saved` 为正，撤销事件为相应负数；起送补单二者均为 0。撤销事件保留原方案金额以便追溯，不表示撤销后发生支付。

建议及事件在 `backend/storage/events.json` 通过临时文件和原子替换保存。读写失败会明确报错；服务重启保留历史，浏览器购物车与待确认状态单独保存在本地。服务通过文件白名单提供页面，不暴露后端源码、依赖或本地记录文件。

## 验证与实验

在 `backend` 目录运行：

```powershell
npm test
node experiments/run-benchmark.js
```

`npm test` 保留引擎、联动前端、历史／看板回归和 API 集成测试。覆盖金额与库存、组合搜索、偏好约束、起送分支、过期校价、采纳撤销、事件幂等、历史筛选分页、旧记录兼容及持久化错误，也覆盖研究任务恢复、计时、复算重试、记录幂等与导出。2026-10-24 v1.4 运行 64 项测试和 26 组 API 集成全部通过，含偏好加权重排（采纳两次饮品方案后「符合我的偏好」将饮品方案排到首位，其他策略保持净省最多优先）与演示数据清零。接口测试使用临时目录和随机端口，不改动本地演示历史。v1.3 的浏览器实测与演示导出见[任务评估验收记录](../output/任务评估验收_v1.3_20261021.md)。

[基准脚本](backend/experiments/run-benchmark.js) 使用固定随机种子、专项边界和独立计价／数量向量穷举参照，分别检查净省与起送场景，并比较不加购、单件及低价前缀贪心策略。参数支持 `--seed N --cases N --perf-samples N`，JSON 输出至 `backend/experiments/results/v14-benchmark.json`，生成 [实验报告](docs/EXPERIMENT_REPORT.md)。性能覆盖 5–50 个候选（50 项为 API 上限，本机单次同步计算约 1–2 秒）。报告中的一致性只针对合成场景和已实现规则；耗时受机器与样本影响，不等同于真实用户收益、平台效果或生产服务等级。
