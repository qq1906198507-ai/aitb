# 智能凑单 v1.5 技术方案

本版本在一个本机 Node.js 服务中同时提供页面和 API。默认监听 `127.0.0.1:3000`，用于产品演示、算法验证与需求核对。没有对接外卖平台、真实支付或生产用户系统。

## 1. 模块与职责

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| API 联动页面 | `mobile-api.html`、`mobile-api-app.js`、`mobile-api-extra.css` | 商品操作、起送提示、偏好、方案比较、采纳/撤销和刷新恢复 |
| 看板 | `dashboard.html`、`dashboard-app.js` | 每 2 秒读取本机事件统计，展示分类采纳、预计净省、趋势和导出 |
| 历史 | `history.html`、`history-app.js` | 筛选采纳/忽略/撤销，以游标加载更多，区分起送补单与净省 |
| 计价与搜索 | `backend/engine.js` | 整数分计价、起送资格、0–4 件组合、预算/排除/库存和排序 |
| API 与校验 | `backend/server.js` | 权威目录规范化、JSON 校验、报价复核、接口路由和页面白名单 |
| 本地存储 | `backend/store.js` | 报价分组、事件状态、幂等、原子落盘、统计与分页 |
| 示例规则 | `backend/data.js` 和服务端默认车 | 本地商品、库存、优惠与 ¥25 起送规则 |
| 独立实验 | `backend/experiments/run-benchmark.js` | 不启动服务，不读取业务存储，生成独立校验及性能报告 |

PC 和静态移动端页面为纯前端单件原型，不使用本机事件统计。完整 v1.5 行为位于 API 联动页。

## 2. 计算请求与返回

页面启动时读取默认车、推荐目录和优惠。用户修改购物车或偏好后，发送 `POST /api/calculate`。以下为起送演示的请求形状：

```json
{
  "currentItems": [{"id":"p2","quantity":1},{"id":"p3","quantity":1}],
  "recommendItems": [{"id":"r1"},{"id":"r2"},{"id":"r3"},{"id":"r4"},{"id":"r5"}],
  "preferences": {"maxItems":3,"maxAdditionCost":10,"excludeIds":[],"strategy":"saving"}
}
```

商品列表分别最多 50 项，ID 必须已知且不重复；原车数量为 1–100 的整数并受库存限制。服务端从目录重建商品，客户端上传价格无法改变计价。请求体最多 64KB；格式错误返回 400。

API 缺省 `preferences` 为最多 2 件、预算不限、无排除和 `saving`。联动页首次默认最多 3 件、商品预算 ¥10；保存过的偏好会恢复。`maxItems=0` 关闭推荐；预算为 `null` 时不限，为数值时须为 0–1000；`strategy` 为 `saving/fewer/preference`。界面名称分别为「支出更低／购买件数更少／符合我的偏好」；`preference` 由服务端按本机演示事件中的品类权重对可行方案做演示级重排，只影响展示次序，不改方案内容与采纳复核（见算法模型第 5.1 节）。响应带 `preference.applied` 与 `preference.affinity` 快照。

常规响应包含：

| 字段 | 含义 |
| --- | --- |
| `breakdown` | 商品、包装、配送、满减、券和总额，以及 `minimumOrder/minimumOrderGap/orderable` |
| `mode`、`reason` | 当前为 `saving` 或 `minimum-order`，以及无解或起送说明 |
| `preferences` | 服务端验证后的偏好 |
| `suggestion`、`alternatives` | 第一方案或 null、最多三种方案；每种包含商品数量、成本、实付、净省及计算步骤 |
| `search` | 件数上限、候选数、评估组合数、`exhaustive`、`degraded` 与剪枝/截断明细及明确搜索范围；目录超过候选上限（默认 24）或搜索超时（默认 90ms）时自动降级并如实标注 |
| `performance` | 本次和进程内最近最多 1000 次同步引擎计算耗时 |

每套已存报价另有 UUID `id`、本次计算的 `groupId`、创建时间和 5 分钟截止时间。`kind` 区分两类方案；起送方案 `netSaving=0`，`paymentChange` 保留有符号估算变化。详细计价与排序见 [算法模型](ALGORITHM_MODEL.md)。

`POST /api/calculate/batch` 使用同样输入规范化与偏好，返回全部可行方案排名和搜索范围，不创建可采纳报价，也不作为单次引擎 `calculate` 性能窗口样本。API 当前没有大目录并发治理。

## 3. 展示、选择与采纳复核

页面打开具体方案时记录 `shown`；单纯计算不算展示。选择采纳或不加购分别记录 `accepted/rejected`。事件接口只接收 `recommendationId/type`，不会信任客户端提交的净省、商品价或统计值。

同一报价每类事件重试幂等，`accepted/rejected` 最终选择互斥；未展示不可决定。展示和采纳需未过期。同一批备选方案最多有一次采纳，即使后来撤销也不能再次采纳同一批报价。

服务端采纳时重新校验优惠规则签名、权威商品价和包装费、库存、件数、商品预算、排除与允许候选范围，再以当前时刻重算原车和加购后金额，核对资格、方案类型、净省及支付变化。发生变化或失效返回 409，页面要求重新计算。报价成功不等于下单，也不预留库存。

已采纳方案可记录一次 `reverted`，保留原事件；页面只向用户提供最近一次采纳、且购物车未另行改变时的撤销。撤销恢复浏览器中的原车，没有真实订单取消、退款或库存回滚操作。

## 4. 持久化与网络失败恢复

`backend/storage/events.json` 保存报价、分组、原始输入、优惠签名和事件。每次更新先构建副本，写入同目录临时文件，再原子替换目标文件；只有成功后才替换进程内状态。失败返回 503，原文件保留，页面可重试。启动发现损坏文件时明确报错而不清空历史。没有事件引用且过期超过一天的报价会在创建后续报价时清理。

浏览器以 `netsave-demo-session-v2` 保存购物车、偏好、最近撤销信息与待确认操作。发送决定前先保存待确认状态，防止响应丢失后重复改变车。刷新或重试时通过 `GET /api/suggestions/:id` 查询最终状态，并在必要时幂等重发，再将服务端决定应用到购物车。待确认期间锁定相关操作；报价失效时保留车并重新计算。

本地 JSON 适合单进程演示。没有多进程锁、事务数据库、账户隔离或跨设备同步保证；不能让多个服务实例并发写同一文件。浏览器状态也不是支付订单或服务端购物车。

## 5. 统计、历史与兼容

有效采纳为未撤销的全部采纳，细分 `savingAcceptedCount` 与 `minimumOrderAcceptedCount`。预计净省只累加净省方案；起送补单采纳和撤销的 `saved` 都为 0。净省采纳的 `saved` 为正，撤销事件为相应负数；统计通过剔除已撤销采纳得到当前净省，避免重复扣回。

采纳率分母为有效采纳加忽略；未决定和已撤销不进入分母。平均采纳净省分母为全部有效采纳，包含起送方案的零贡献。近 7 天按 `Asia/Shanghai` 的采纳日期汇总。旧记录缺少 `kind` 时按净省方案兼容，缺少补充金额时从已存报价回填公开字段，不改写旧记录。

历史接口 `GET /api/history` 支持 `type=all/accepted/rejected/reverted`、`limit=1…100`，`before` 为上一页末事件 UUID；首屏省略游标。按事件写入顺序倒序分页；`total` 为当前类型全部匹配条数。展示事件用于统计，不出现在历史列表。看板失败保留最后成功快照并标明状态；历史页进入、恢复前台或手动刷新时重新读取。

## 6. 接口与运行边界

除计算和事件外，还提供 `/health`、`/api/cart/default`、`/api/products/recommend`、`/api/promotions`、`/api/suggestions/:id`、`/api/dashboard` 和 `/api/history`。页面使用显式文件白名单提供，后端源码、依赖与存储文件没有静态公开路由。响应设置 `Cache-Control: no-store`。

当前为本机可信演示环境，未实现鉴权、用户隔离、限流或支付能力；服务启用了 CORS。默认回环监听有助于限制访问范围，但不构成生产安全方案。实际部署前需增加身份与权限、输入规则管理、数据库事务、审计、容量测试和监控，并重新评估跨域与网络暴露策略。

## 7. 验证入口

在 `backend` 运行 `npm test` 执行引擎、联动页面、历史/看板和 API 回归。接口测试使用临时存储和随机端口，不改演示历史。独立实验执行：

```powershell
node experiments/run-benchmark.js --seed 20261020 --cases 240 --perf-samples 40
```

脚本只加载引擎，自行实现计价、数量向量穷举和基线；固定业务时刻避免到期漂移，JSON 保存全部输入、目标、违规和原始耗时。实际数值与局限见 [实验报告](EXPERIMENT_REPORT.md)。测试通过不代表已完成平台接入、真实支付对账或业务转化验证。

## 8. 真实用户验证与业务评估方案

当前交付只验证原型交互、计价和有限搜索的一致性。本节是后续实验设计，不是已完成的用户研究或 A/B 结果。启动业务实验前，先接入并对账真实商品价格、起送门槛、满减与券规则、库存、配送及包装费用；建立用户级随机分组、曝光和订单事件关联，并定义取消、退款、优惠成本和异常订单口径。

### 8.1 可用性任务测试

先对照现有人工流程开展小规模、带观察的任务测试，任务分为“差一点到起送价”和“差一点享受满减”两类，采用反平衡顺序以减少练习顺序影响。每个任务固定购物车、可选商品和优惠条件，要求参与者判断是否需要补单、选出符合自己约束的方案并说明预期实付。记录从任务开始到最终选择的时间、任务完成率、金额判断正确率、加购件数与金额、放弃或无解原因和主观费力度；按场景分开报告，并保留原始任务定义与匿名化记录。另询问加购商品是否符合原有需求、是否只是为达门槛而买；件数、预算和排除项只是约束手段，不能单凭更少件数声称减少了不必要购买或浪费。该阶段用于发现理解错误和流程阻塞，样本较小时只作可用性诊断，不外推总体效果。

#### 已提供的本地任务工具

`research.html` 使用冻结任务版本 `1`、固定计价时间 `2026-10-20T07:00:00.000Z`、¥10 加购商品预算和最多 3 件约束。`GET /api/research/tasks` 提供任务，`POST /api/research/solve` 求解，`POST /api/research/evaluate` 独立复算；研究接口使用独立计算实例，不创建可采纳报价，不写业务事件，也不进入主引擎性能样本。

研究员安排手动或智能方式，参与者显式开始计时；提交选择时固定决策时间，复算请求耗时和后续反馈不计入决策用时。刷新和离开页面时间包含在决策时间内并记录中断；反馈提交后才显示复算答案。记录包含任务版本、固定计价时间、匿名编号、选择、预估金额、复算差额、购买意愿与主观费力度，可导出 JSON/CSV；起送原车不可下单，补单支付变化不算净省，放弃任务不生成金额判断误差。

进行中进度与完成记录均保存在本浏览器；完成记录按 `recordId` 分条保存并去重，旧聚合数组兼容读回。进度或复算失败可重试，版本变化和损坏进度有明确退出入口。一个浏览器一次只开展一个任务，不支持跨设备同步或并行多标签任务。工具不随机分组；当前两条 `DEMO-QA-20261021` 记录仅为自动化操作演示，不能比较两种方式的效率。验证证据见[任务评估验收记录](../../output/任务评估验收_v1.3_20261021.md)。

### 8.2 随机对照 A/B

完成真实规则对账和可用性修正后，对满足条件的结算会话做用户级 1:1 随机分组：对照组使用现有结算与手动凑单流程，实验组在相同商品、价格、优惠和库存下展示智能方案。以首次分组固定用户归属，分析按意向治疗（ITT）进行。实验分层在推荐展示前、按首次符合条件的原购物车状态固定：商品小计低于起送门槛的“起送未达标”组，以及已达起送且距预先定义满减门槛不超过预设金额的“临近满减”组；实验期间不因加购后的购物车状态重新筛选或改变分层。曝光、方案展示、采纳、提交订单、支付、取消和退款均使用同一可追溯会话 ID，支付结果与订单系统对账。

| 指标类型 | 预先定义的口径 |
| --- | --- |
| 决策效率 | 从结算页进入到用户提交订单或明确退出的时间分布；同时报告在预设观察窗内完成决策的比例，未完成会话单独计数，避免只比较成功者造成偏差 |
| 下单结果 | 每个符合条件的随机分组会话中至少完成一笔支付的会话数／合格会话数；另报每会话已支付订单数、提交率及取消／退款率，分母和观察窗固定 |
| 用户凑单成本 | 每个符合条件会话的加购件数、加购商品金额和包装／配送变化；对净省场景另核对平台实付差额，对起送场景报告达标所需增支，不把估算差额称为节省 |
| 平台交易指标 | 每个符合条件会话的已支付订单金额，扣除取消与退款后报告净支付额；订单数和净支付额分别报告，不以加购金额或未支付订单替代交易结果 |
| 护栏指标 | 取消／退款、投诉、无货或报价失效、优惠成本、商家及平台毛利影响和服务延迟；预先设定不得恶化的容忍界限；用预设抽样问卷跟踪用户认为不需要的加购，区分自报购买意愿与实际食物浪费 |

实验开始前，根据历史基线、预先指定的最小业务重要差异、显著性水平和统计功效计算所需用户数与持续时间，并记录每用户会话次数。推断和置信区间以用户为随机化单位，对用户的重复会话按用户聚类或先汇总到用户级，避免把同一用户的会话当作独立样本而夸大精度；会话级业务指标可报告点估计，但推断仍需尊重用户级随机分组。固定主指标、分层和分析方案，避免中途挑选有利指标。报告组间差异、置信区间、样本流失和护栏结果。只有当支付订单或扣除取消退款后的净支付额达到预注册的业务判定标准，且护栏不越界时，才可报告相应业务提升；否则报告未观察到提升或证据不足。所有效果结论须基于真实平台订单、支付与优惠成本数据，本地看板和合成基准不能替代这些证据。

### 8.3 分阶段准入

1. **数据与规则验收：** 对平台计价、门槛、优惠互斥、账户资格、库存及支付账单做逐单对账；未通过前不以原型金额作为实验结果。
2. **任务可用性验收：** 修复造成误解或错误下单的高频问题；确认两类任务的计时、分母和事件采集可用。
3. **受控 A/B：** 预注册方案，完成样本量评估和用户级随机分流，持续监控护栏；达到预定样本量和观察窗后再分析。
4. **扩量决策：** 仅依据真实支付结果、统计不确定性、优惠补贴及取消退款等指标决定是否扩大流量。此原型尚未达到上述准入条件。
