# 智能凑单 v1.5 算法模型

本模型对应 `backend/engine.js`。它在给定商家、商品目录、库存和显式优惠规则内决定加购哪些商品及数量，保留原购物车。它是有限约束组合搜索；偏好加权（第 5.1 节）是展示层重排，实时降级（第 5.2 节）是大目录下的预算内求解，均不含训练模型、真实用户偏好推断或跨平台最优性主张。

## 1. 输入、时间与金额

原购物车为 C，候选商品为 i=1…n。商品包含原价、可选限时价及截止时刻、库存、品类和每件包装费。一次计算固定同一时刻 t；限时价在 `t < endTime` 时生效，达到截止时刻即恢复原价。当前实现未设置限时价开始时间字段。

金额先按最近的整数分取整，再累加；输出明细为两位小数字符串，方案金额为元数值。服务端目录与优惠是权威来源，客户端上传的单价、包装费和库存不会覆盖目录。

令 p_i(t) 为活动后的单件商品价，b_i 为单件包装费，q_i 为购物车中的数量。定义：

```text
商品小计 S(C,t) = Σ p_i(t) × q_i
包装费 B(C) = Σ b_i × q_i
```

所有求和均在整数分上进行。包装费缺省为 0；本地示例商品目前为 0，但非零包装费已纳入引擎、采纳复核和专项实验。

## 2. 起送资格与计价顺序

起送门槛 M 独立于免配送门槛 H。非空车且 `S >= M` 才可下单；未配置 M 时按 0。起送差额为 `max(0, M-S)`。起送按活动后、满减与券之前的商品小计判定，包装费和配送费均不参与。

配送费 D 由两部分组成：`S < H` 时收基础配送费，否则免基础配送费；处于启用的高峰时段时，独立加收一次高峰费。时段端点当前包含在内，跨午夜时段需要拆成两个时段。运行时按服务端本地时区取时；当前演示环境使用北京时间。实验显式固定 `Asia/Shanghai`。

满减在商品小计达到的规则中选择**折扣金额最大的一档**，不累加多档；折扣 R 至多为商品小计。优惠券先按商品小计门槛、开始/结束时间及可选品类资格过滤。开始时刻包含，结束时刻不包含；品类券只要求车内出现该品类，并未限制优惠只能抵该品类金额。随后选用全部 `stackable: true` 券和一张面额最大的非叠加券。当前规则允许券抵商品、包装与配送合计的剩余金额，并将实际券优惠 Q 截断至该剩余金额，保证实付非负：

```text
R = min(S, 最大可用满减折扣)
Q = min(S+B+D-R, 全部可叠加券面额之和 + 最大非叠加券面额)
T(C,t) = S+B+D-R-Q
```

空购物车的全部费用为 0，资格为不可下单，也不生成加购推荐。上述抵扣口径是本地简化规则；接入平台时需按平台分别配置优惠门槛基数、抵扣范围和互斥关系。

## 3. 决策变量与用户约束

对每个合法候选决定整数数量 x_i。已在原车中的商品、显式排除商品、无库存商品与重复 ID 被排除。当前不对原车商品追加同款数量；候选商品之间允许同品多件及异品组合。

```text
x_i ∈ {0,…,stock_i}，未配置库存时只受件数上限约束
1 <= N(x)=Σx_i <= K，K ∈ {0,1,2,3,4}
A(x)=Σp_i(t)×x_i <= U（U为空时不设商品预算）
x_i=0，对所有排除商品
```

K=0 表示不生成推荐。预算 U 为 0–1000 元，只约束加购商品价 A；新增包装费和配送变化计入最终实付，但不计入商品预算。界面将该字段标为「加购商品预算」。服务端拒绝无效件数、预算、策略和未知/重复排除 ID。

API 缺省偏好是 K=2、预算不限、无排除、`strategy: saving`。联动页面首次使用的默认值是 K=3、商品预算 ¥10、无排除和「支出更低」；浏览器会保存用户修改后的偏好。

## 4. 两种决策目的

设原车估算或实付为 T0，加购后实付为 T1。所有返回方案都必须使加购后的车可下单，并满足以上约束。

| 模式 | 触发条件 | 额外可行性条件 | `netSaving` | `paymentChange` |
| --- | --- | --- | --- | --- |
| `saving` | 原车非空且已可下单 | T1 < T0 | T0−T1，严格为正 | T1−T0 |
| `minimum-order` | 原车非空且未达起送 | 达到起送即可，允许增加支出 | 固定为 0 | T1−T0，可正可负 |

原车不可下单时，T0 仅为按同一计价公式得到的估算，不能作为实际可成交订单的节省基线。因此即使补单使估算金额降低，也不计为净省。

## 5. 排序与搜索

「支出更低」（`saving`）按 `(T1, N, A)` 升序排列；「购买件数更少」（`fewer`）按 `(N, T1, A)` 升序排列。两者都是字典序：先比较第一项，相同时比较下一项。在净省模式中，少买优先仍只在正净省的可行方案内选择。最后以商品 `id×数量` 串的字典序打破平局，使相同输入下排序稳定。

引擎按递增候选索引逐一选择商品及其数量，预算或库存不满足时剪枝；每一种非空数量组合只评估一次。它不提前停在第一种可行解，不静默截断已声明的搜索空间。全部合法方案排序后，常规计算返回前三种；批量接口返回全部可行排名。

若无库存和预算限制，最多 K 件的非空组合数为 `C(n+K,K)-1`。例如 K=4 时，5、10、20 个候选分别有 125、1000、10625 种数量组合。计价与全量排序还带来额外开销，不能只根据件数上限假设大目录会立即完成。`search` 返回候选数、评估组合数、上限和搜索范围，`exhaustive: true` 只表示在这些已说明约束内穷举。

### 5.1 偏好加权重排（`preference`，演示级）

第三种策略「符合我的偏好」不改变候选集、可行性与方案内容，只在服务端返回前对方案次序做一次重排。品类权重 w(c) 全部来自本机演示事件（`store.categoryAffinity()`）：采纳净省方案每品类 +1、采纳起送补单 +0.5、忽略 −0.75、撤销 −1.5，逐事件累加并截断到 [−3, +3]；没有品类字段的旧事件不计。权重为 0 时该策略退化为「支出更低」排序。

```text
净省方案得分 = 净省金额(分) + 50 × Σ w(品类)
起送方案得分 = −支付变化(分) + 50 × Σ w(品类)
按得分降序；平局沿用 (T1, N, A, id×数量) 字典序
```

其中 50 分相当于每点品类权重 ¥0.50。该重排只影响展示次序：`netSaving`、实付、价格明细与采纳复核口径全部不变，被采纳方案的复核仍按原计价规则逐项重新推导。响应中的 `preference.applied` 表示本次确实发生了加权（有非零权重），`preference.affinity` 是当前品类权重快照。它是基于本机演示行为的启发式排序，不是经真实用户数据训练的模型，也不预测用户意愿。

### 5.2 实时预算与降级求解（v1.5）

组合数 `C(n+K,K)-1` 随候选数 n 快速增长：n=20 时约 1.1 万，n=50（API 上限）时 31.6 万，本机全量穷举约 1 秒。为兑现「不阻塞下单」的延迟承诺，引擎引入两级降级，均由接口如实标注：

1. **候选剪枝**：候选超过 `searchCandidateLimit`（默认 24）时按活动价升序做**价格分层轮转保留**——从最低价层开始每层取一个、逐层补足到上限。纯低价截断会整体丢掉高价档、错过「加几件跨满减档」的组合（实验中首选目标与全量穷举不一致）；分层轮转保留全部价格档位后，50 候选下 61ms 找到与 916ms 全量穷举一致的首选目标（见实验报告「实时降级」节）。
2. **预算截断**：搜索超过 `searchBudgetMs`（默认 90ms）时立即停止展开，返回已评估出的方案。评估每 256 个组合检查一次时钟。

降级只影响搜索空间，不影响正确性：任何返回方案仍由同一计价函数推导、满足全部约束，采纳复核逐项重新校验。`search.exhaustive=false`、`search.degraded=true` 及 `degradation`（剪枝/截断/预算/耗时）随响应返回，界面在方案区标注「实时预算内求解」。两项阈值是引擎构造参数，实验与测试通过调小阈值确定性触发降级路径；阈值为 0 表示关闭对应机制。

## 6. 两个反例与可核对示例

原车商品 ¥18、起送 ¥20、候选 ¥2 时，补单后支出增加也应返回可达起送方案；这与只返回正净省的推荐不同。

原车 ¥47、满 ¥50 减 ¥10、候选每件 ¥1 且库存 3 时，单件或两件搜索无解；三件可使实付从 ¥47 降至 ¥40，净省 ¥7。若原车 ¥46，则必须四件才能达到同一门槛；最多三件时不能声称存在方案。

默认演示车商品小计 ¥48，非高峰时配送已免，满减 ¥5，券共 ¥8，实付 ¥35；加购 ¥2 米饭到 ¥50，满减变 ¥10，券仍 ¥8，实付 ¥32，净省 ¥3。该例的包装费为 0。

## 7. 证据与边界

[可复现实验报告](EXPERIMENT_REPORT.md) 使用独立计价和数量向量穷举参照，检查首选目标、无解结论及全部返回方案的金额与约束；专项涵盖三/四件门槛、包装、预算、排除和时效。实验不构成所有输入的形式化证明，不证明真实订单收益或用户转化提升。当前模型不包含换掉原车商品、跨店、复杂券互斥、账户资格、库存预留、配送地域差异或真实支付对账。
